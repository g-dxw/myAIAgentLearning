# 最终确认问题决策记录（FQ1-FQ6）

**决策日期**：2026-05-18
**状态**：已全部确认，已集成至 PRD

## FQ1 - 护工提交的病人补充信息是否需要管理员审核？

**决策**：AI 完整性校验通过后直接更新病人档案，**不需要管理员审核**。仅管理员可以直接手动编辑长期记忆；护工提交的信息经 AI 校验后自动更新。

**Why**：精简业务流程，信任护工现场采集 + AI 校验。如后续出现质量问题，Phase 2 引入管理员抽审机制。

**影响**：Session 模型的 PENDING_REVIEW/APPROVED 状态已移除，改为 ONGOING/COMPLETED。版本追踪字段 update_method 区分 admin_manual 和 ai_supplement。

## FQ2 - 补卡是否必须关联排班？

**决策**：补卡**可以不关联排班**。`schedule_id` 为可空字段，护工可在补卡页面直接填写病人、服务时段和护理内容，即使没有预先生成排班记录也可以发起补卡。

**Why**：覆盖护工未按排班执行但仍需记录服务的情况，提供灵活性。

## FQ3 - Session 对话轮次的上下文策略

**决策**：采用策略 C —— **保留全部历史 + AI 自动摘要**。
- 每次护理记录对话保留 Session 内完整聊天历史
- AI 在每轮对话结束后自动生成本轮总结
- 新对话以"历史摘要 + 近期消息"作为上下文输入

**Why**：确保 AI Agent 具有"长期记忆"，同时通过摘要机制控制上下文窗口长度。

## FQ4 - 出勤统计的绩效字段范围

**决策**：仅预留 `score`（Integer） + `performance_level`（String）两个字段。Phase 1 不展示绩效指标，仅数据预留。

**Why**：满足未来扩展需要，避免过度设计。Phase 2 设计绩效考核模块时再行扩展。

## FQ5 - App 形态

**决策**：Phase 1 仅支持**移动 Web 浏览器**，不提供 PWA，不提供原生 App。

**Why**：降低 Phase 1 交付复杂度，移动 Web 足以覆盖护工核心操作场景。

## FQ6 - 补卡跨日的边界定义

**决策**："同一天"的边界 = **排班所属的日历日期**。无关联排班时 = **补卡提交当日的日历日期**。

**Why**：提供清晰的日期边界判定规则，避免歧义。若有排班则以排班日期为准，若无排班则以提交日期为准。
