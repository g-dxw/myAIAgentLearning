## 1. 背景与问题陈述

### 1.1 行业背景

中国老龄化进程加速，养老服务机构对信息化管理工具的需求急迫。当前大量中小型养老机构仍依赖纸质记录 + 微信沟通，存在以下痛点：

- **排班混乱**：护工排班靠人工协调，冲突频发，临时调整靠电话沟通，效率低下
- **护理记录不完整**：护工上门服务后记录随意，缺乏标准化检查，管理层无法有效追溯服务质量
- **病人信息分散**：病人基本信息、监护人情况、基础疾病等关键信息散落在不同渠道，无法集中管理
- **新人审核缺失**：新增病人缺乏标准化审核流程，信息录入质量参差不齐
- **监管盲区**：管理层无法实时掌握护工在岗/缺勤状态，服务完成情况不可见

### 1.2 本次建设目标

构建一套面向养老机构的双端管理系统：
- **机构端（Web）**：管理员统一管理护工、病人、排班、护理记录
- **护工端（Mobile Web）**：护工上门服务的移动工作台，含 AI Agent 辅助对话、打卡、记录提交

本次 PRD 覆盖 **Phase 1**（首批交付范围），后续 Phase 将补充预警、投诉、加钟、多机构等功能。

## 2. 目标用户与角色

| 角色 | 系统端 | 说明 |
|------|--------|------|
| 机构管理员（Admin） | 机构端 Web | 系统唯一管理员，负责护工/病人/排班/记录等全部管理工作 |
| 护工（Worker） | 护工端 Web（移动优先） | 上门服务的执行者，使用 AI Agent 完成病人信息补充、打卡、提交护理记录 |
| 病人（Patient） | 数据实体 | 接受服务的老年人，信息由管理员录入、护工补充完善 |
| 家属（Family） | 非直接用户（Phase 1） | 未来可通过系统查看老人情况，Phase 1 不涉及 |

**机构数量**：单机构模式。Phase 1 仅支持一个养老机构使用，不区分多租户。

## 3. 目标与成功指标

| 目标 | 衡量方式 | 目标值 |
|------|----------|--------|
| 护工排班冲突归零 | 系统排班表查重 | 0 冲突 |
| 护理记录提交率 | 已提交记录 / 应提交总数 | >= 90%（首月） |
| 病人信息完整度 | 所有必填字段完成率 | 100%（Phase 1 结构化字段） |
| 护工打卡率 | 实际打卡次数 / 排班次数 | >= 85% |
| 病人新增审核效率 | 从申请到审批完成时间 | <= 2 个工作日 |
| 缺勤可追溯率 | 未打卡记录标记为旷工 | 100% |

## 4. Phase 1 范围声明

### 4.1 纳入范围

| 模块 | 范围 |
|------|------|
| 认证系统 | 管理员预置账号登录；护工使用身份证后 6 位登录 |
| 护工管理 | 增删改查、启用/停用（停用时自动取消待执行排班） |
| 病人管理 | 管理员新增（走审核自批）、字段补全、列表/详情查看；**不含批量导入** |
| 排班管理 | 24 小时手动排班（1 小时粒度）、**双入口（按病人/按护工）**、空闲/忙碌状态可视化、人员冲突检测、**代班手动重分配** |
| AI Agent 对话 | 护工对已分配病人进行信息补充对话、AI 提取结构化数据、护工编辑+二次确认、**每个病人一个长期 Session（长期记忆模式）** |
| 打卡 & 护理记录 | 开始/结束打卡（**从排班详情页进入**）、提交护理记录、当日补卡（**自由填写时段，不自动关联排班**）、未提交=旷工、**旷工统计列表**、**管理员可纠正旷工状态** |
| 系统管理 | 基础参数配置、旷工状态纠正、密码重置线下通知、**绩效字段预留** |

### 4.2 明确排除（Phase 2+）

- 投诉管理（全部排除）
- 预警系统（AI 健康分析、预警推送、风险等级）
- 加钟/临时调整排班
- 自动排班算法
- 护工离职流程
- AI 护理记录完整性评分
- 批量导入病人
- 多机构/多租户
- 家属端

## 5. 功能需求详述

### 5.1 认证系统（AUTH）

#### 5.1.1 管理员账号

- **预置账号**：用户名为 `admin`，密码为 `fd7105203322`
- 管理员账号在系统初始化时通过种子数据写入数据库，**不提供注册入口**
- 密码经过 bcrypt 加盐哈希后存储
- 管理员不可被删除，不可被停用

#### 5.1.2 护工账号

- 护工账号在"新增护工"时自动创建
- 默认密码：**身份证号码后 6 位**
- 角色固定为 `worker`
- 管理员可在护工详情页重置护工密码（重置规则同上）
- 护工首次登录不强制修改密码（Phase 1 不做首次登录引导）

#### 5.1.3 登录流程

- 输入用户名 + 密码 → 服务端校验 → 返回 JWT token（有效期 24 小时）
- 系统根据用户角色（admin / worker）跳转到对应的布局页面
- Token 过期后需重新登录，不提供 refresh token 机制

#### 5.1.4 后端 API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/login` | 登录，参数 { username, password }，返回 { token, user } |
| GET | `/api/auth/me` | 获取当前登录用户信息 |

### 5.2 护工管理（WORKER）

#### 5.2.1 护工字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 姓名 | string(50) | 是 | |
| 手机号 | string(20) | 是 | 格式校验 |
| 身份证号 | string(18) | 是 | 唯一；用于生成默认密码 |
| 头像 | string(255) | 否 | 图片 URL |
| 状态 | enum | 是 | active / inactive |

#### 5.2.2 功能要求

1. **新增护工**：管理员填写姓名、手机号、身份证号 → 自动创建关联 User 账号（密码=身份证后 6 位）→ 护工默认状态为 active
2. **编辑护工**：管理员可修改姓名、手机号、头像（身份证号不可修改）
3. **停用护工**：将护工状态置为 inactive，系统**自动取消该护工所有待执行的排班**（状态变为 cancelled）
4. **启用护工**：将护工状态置为 active
5. **删除护工**：物理删除，仅允许删除无关联排班/打卡/记录的护工；若有历史关联数据则逻辑删除（状态标记为 deleted，保留数据完整性）
6. **护工列表**：分页展示，支持按姓名/手机号/状态筛选

#### 5.2.3 护工离职流程

Phase 1 **不包含**完整的离职审批流程。管理员通过手动启用/停用管理护工状态。完整的离职交接流程预留至后续版本。

#### 5.2.4 后端 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/workers` | 护工列表（分页+筛选） |
| GET | `/api/workers/:id` | 护工详情 |
| POST | `/api/workers` | 新增护工（自动创建 User） |
| PUT | `/api/workers/:id` | 编辑护工 |
| DELETE | `/api/workers/:id` | 删除护工（含数据完整性检查） |
| PATCH | `/api/workers/:id/status` | 启用/停用护工 |

### 5.3 病人管理（PATIENT）【关键变更】

#### 5.3.1 病人字段（完整版）

基于 Q10 的答复，病人字段如下。**当前数据库模型需要扩展**，新增医保类型、监护人情况等字段。

| 字段 | 类型 | 必填 | 录入方 | 说明 |
|------|------|------|--------|------|
| 姓名 | string(50) | 是 | 管理员 | |
| 年龄 | int | 是 | 管理员 | |
| 性别 | string(4) | 是 | 管理员 | 男/女 |
| 医保类型 | string(20) | 是 | 管理员 | 城镇职工/城乡居民/自费/其他 |
| 联系电话 | string(20) | 是 | 管理员 | |
| 居住地址 | string(200) | 是 | 管理员 | |
| 监护人情况 | text | 否 | 护工补充 | 文字描述，尽量详细（与关系、联系方式等） |
| 紧急联系人 | string(50) | 是 | 管理员 | 姓名+关系+联系电话 |
| 基础疾病信息 | text | 否 | 护工补充 | 文字描述，尽量详细 |
| 照护要求 | text | 否 | 护工补充 | 文字描述，尽量详细 |
| 性格特点 | text | 否 | 护工补充 | 文字描述，尽量详细 |
| 状态 | enum | 自动 | 系统 | active / pending |
| 所属护工 | FK | 是 | 管理员 | 当前负责该病人的护工 |

#### 5.3.2 病人新增流程（关键变更）

**新流程**（基于 Q12 调整）：

```
Step 1: 管理员填写病人基本信息（姓名/年龄/性别/医保类型/联系电话/居住地址/紧急联系人）
         + 指定负责护工
         → 提交后状态为 pending（待审核）

Step 2: 系统触发管理员的"自审核"
         → 管理员在审核列表看到自己提交的病人申请
         → 管理员确认通过 → 病人状态变为 active
         → 管理员驳回（极少发生，但有兜底通道）

Step 3: 病人进入 active 状态后
         → 被分配的护工在自己的工作台看到该病人
         → 护工上门服务时，通过 AI Agent 对话补充详细信息
         → 补充内容：监护人情况、基础疾病信息、照护要求、性格特点

Step 4: 护工提交补充信息
         → AI 校验信息完整性
         → 校验通过 → 信息保存至病人档案
         → 校验不通过 → 提示缺失项，护工补充后重新提交
```

**设计要点**（FQ1 已确认）：
- 管理员新增病人仍需走审核流程，保持系统工作流统一
- 审核人为同一管理员（自提自审），但系统保留完整的操作记录
- 护工不能新增病人，只能对已分配的病人补充信息
- **护工通过 AI Agent 提交的补充信息，AI 完整性校验通过后直接更新至病人档案，无需管理员审核。** 这是最终确认的设计决策。如有后续质量问题，Phase 2 可引入管理员抽审机制。

**版本追踪**（Q26）：病人档案作为"长期记忆"，每次信息更新系统自动记录：
- **最后更新人**：管理员 ID 或护工 ID
- **更新方式**：枚举值（admin_manual / ai_supplement）
- **更新时间**：datetime

该信息在病人详情页底部以时间线方式展示。护工端可见但不可修改版本追踪信息。

#### 5.3.3 特殊情况记录

| 字段 | 类型 | 说明 |
|------|------|------|
| 类型 | enum | 固定 4 值：死亡、就医、外出、其他 |
| 描述 | text | 具体情况描述 |
| 记录时间 | datetime | 自动生成 |

- 管理员可对 active 病人新增特殊情况记录
- 在病人详情页以列表形式展示
- 特殊情况仅用于信息记录，不影响病人状态（Phase 1 不做自动状态变更）

#### 5.3.4 批量导入（明确排除）

**Phase 1 不支持批量导入**。如需批量新增病人，管理员需逐个手动操作。批量导入功能规划在 Phase 2+。

#### 5.3.5 病历版本追踪（新增，Q26）

病人档案作为"长期记忆"，需要记录每次更新的来源：

| 追踪字段 | 类型 | 说明 |
|---------|------|------|
| last_updater_id | Integer FK | 最后更新人（worker_id 或 admin_id，根据 update_method 区分角色） |
| update_method | enum | admin_manual（管理员手动录入）/ ai_supplement（AI 从护工对话中提取补充） |
| updated_at | datetime | 更新时间 |

护工端可见但不可修改版本追踪信息。管理端在病人详情页底部以时间线展示版本历史。

### 5.4 排班管理（SCHEDULE）

#### 5.4.1 排班规则

| 规则 | 说明 |
|------|------|
| 排班粒度 | 1 小时为单位 |
| 时间范围 | 全天 24 小时可选 |
| 人员匹配 | 严格 1:1：一个时间段内，一个护工对应一个病人 |
| 排班方式 | **仅手动排班**（管理员操作），不包含自动排班算法 |
| 加钟调整 | Phase 1 不包含 |

#### 5.4.2 功能要求

1. **排班视图（双入口，Q22）**：
   - **病人优先入口**：选择一个病人 → 查看该病人当天的排班时间线 → 为该病人指派护工到空闲时间段
   - **护工优先入口**：选择一个护工 → 查看该护工当天的排班时间线 → 为该护工分配病人到空闲时间段
   - 两种视图均使用 24 小时横轴（行=护工，列=时间；或行=病人，列=时间），管理员可通过切换按钮自由切换视角
   - 每个单元格显示该时段服务的病人/护工姓名，空闲单元格显示为空白
   - 顶部：日期切换（前一天/后一天/今天）

2. **新增排班**：
   - 管理员选择一个空闲时间段 + 空闲护工 + 病人 → 创建排班
   - 系统自动校验冲突（护工同一时段已被占用、病人同一时段已有服务）

3. **代班/替换（Q22）**：
   - 当护工 A 无法值守某排班时，管理员需**手动两步操作**完成代班：
     - 步骤一：取消护工 A 的原有排班（状态变为 cancelled）
     - 步骤二：为该病人重新创建排班并分配护工 B
   - Phase 1 不提供一键代班或自动推荐替换人员功能
   - 代班操作后，系统在排班变更日志中记录原护工、新护工及操作时间

4. **编辑/取消排班**：
   - 管理员可修改排班（调整时间段或护工）
   - 管理员可取消排班（状态变为 cancelled）

5. **护工端查看**：
   - 护工只能查看自己的排班
   - 按日期展示，默认显示今天
   - 展示格式：时间区间 + 病人姓名 + 病人地址

6. **冲突检测**：
   - 新增排班时系统自动检测，不允许出现：
     - 同一护工在同一时间段有多个排班
     - 同一病人在同一时间段有多个排班
     - 已被停用/删除的护工参与排班
   - 检测结果在前端直接展示（红色提示），不允许提交

#### 5.4.3 后端 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/schedules` | 排班列表（按日期筛选，支持查看空闲/忙碌状态） |
| POST | `/api/schedules` | 新增排班（含冲突检测） |
| PUT | `/api/schedules/:id` | 编辑排班 |
| DELETE | `/api/schedules/:id` | 取消排班 |
| GET | `/api/schedules/logs` | 排班变更日志（含代班记录） |
| GET | `/api/schedules/my` | 护工端：我的排班 |

### 5.5 护工端 — AI Agent 对话（SESSION）【关键变更】

#### 5.5.1 概念变更说明

**旧流程（废弃）**：护工通过 AI 对话新增病人 → AI 提取信息 → 管理员审核 → 病人入库

**新流程（本次实现）**：
1. 管理员录入病人并分配护工（见 5.3.2）
2. 护工在移动端的"我的病人"列表中看到已分配的病人
3. 护工点击病人 → 进入 AI 对话 session
4. 系统给出初始指引："请在对话中补充该病人的详细信息"
5. 护工通过对话补充：监护人情况、基础疾病、照护要求、性格特点
6. AI 从对话中提取结构化信息
7. **护工可见并可编辑 AI 提取结果**
8. **护工需要二次确认**（Two-step confirm）后才提交
9. 提交后 AI 做完整性校验（检查关键字段是否已填写）
10. 校验通过 → 信息更新到病人档案
11. 校验不通过 → 提示缺失项，护工补填

**Session 生命周期（Q21）**：
- 每个病人有且仅有一个长期 Session，类似于"长期记忆"
- 病人信息通过每日护理记录对话逐步累积和精炼
- **每条护理记录是 Session 内的一个新的对话轮次**，而非创建新 Session
- 护工通过 AI Agent 对话补充的信息，经 AI 提取 + 完整性校验后更新至病人档案
- **只有管理员可以直接修改病人档案**（长期记忆的基础信息）
- 护工不可直接编辑已归档的病人基础信息，但通过每日护理记录提交间接贡献补充内容
- 补充内容需经 AI 提取和完整性校验，之后更新到档案中（版本追踪见 5.3.5）
- Phase 1 实现"一个病人一个 Session"模式；Phase 2 可扩展支持多 Session 追加补充

**会话上下文策略**（FQ3 已确认）：
- 采用 **"保留全部历史 + AI 自动摘要"** 策略
- 每次护理记录对话保留该病人 Session 内的完整聊天历史
- AI 在每轮对话结束后自动生成本轮总结（summary）
- 当护工进入同一病人的新对话轮次时，以"历史摘要 + 近期消息"作为 AI 上下文输入
- 该策略确保 AI Agent 具有"长期记忆"，同时通过摘要机制控制上下文窗口长度

#### 5.5.2 功能要求

1. **病人列表**（护工端）：
   - 展示分配给当前护工的所有 active 病人
   - 每个病人卡片显示：姓名、地址、信息完整度状态（已完善/待完善）
   - 点击进入对话页

2. **对话页面**：
   - 上方展示病人基本信息（姓名、年龄、性别、地址）
   - 下方为聊天区域，初始有一条系统消息提示当前待补充的信息项
   - 护工以自然语言输入信息（或选择系统推荐的追问）
   - AI 回复引导护工逐步完善各项信息

3. **AI 提取结果**（关键功能）：
   - 护工点击"查看提取结果"按钮
   - 弹窗或以嵌入卡片展示 AI 从对话中提取的结构化信息
   - 护工**可以直接编辑**提取结果中的每个字段
   - 编辑后点击"确认提交"（第一步确认）
   - 系统弹出二次确认对话框："提交后将更新病人档案，是否确认？"（第二步确认）
   - 确认后提交 AI 做完整性校验

4. **完整性校验**：
   - AI 检查以下字段是否已填写：基础疾病信息、照护要求（不强制要求一次完成）
   - 缺少关键信息 → 返回缺失列表 → 护工继续补充
   - 全部填写 → 信息写入病人档案 → session 标记为 completed

5. **历史记录**：
   - 护工可查看对同一病人的历史对话记录
   - 每次补充的内容按时间线展示

### 5.6 打卡 & 护理记录（CHECKIN & CARE RECORD）

#### 5.6.1 打卡流程

**入口**（Q27）：护工从今日排班列表中点击某排班卡片 → 进入排班详情页 → 在详情页内点击"开始服务"按钮。排班卡片上**不直接放置**"开始服务"按钮。

```
排班时间到达前/后
  → 护工查看今日排班列表
  → 点击排班卡片进入排班详情页
  → 点击"开始服务"按钮
  → 打卡记录创建（status=STARTED，记录 start_time）
  
服务结束后
  → 护工填写护理记录内容
  → 提交
  → 打卡结束（status=COMPLETED，记录 end_time）
  → 生成 CareRecord

若护工忘记提交：
  → 系统标记该排班为"未提交"
  → 记为旷工（status=ABSENT）
```

#### 5.6.2 功能要求

1. **开始服务**：
   - 护工从"今日排班"列表选择要服务的病人
   - 点击"开始服务" → 打卡开始 → 计时器启动
   - 打卡记录状态为 STARTED

2. **提交护理记录**：
   - 护工填写护理内容（自由文本，后续版本可增加结构化模板）
   - 提交 → 打卡结束 → 生成 CareRecord
   - **AI 完整性评分**：Phase 1 **不包含**，Phase 1 仅跟踪提交/未提交状态
   - 提交后不可修改（Phase 1）

3. **补卡（Q23, FQ2, FQ6）**：
   - 当日内允许补打卡（例如服务结束后忘记提交，但在当天 24:00 前可以补提）
   - **打卡时间记录为实际提交时间**（非计划服务时间）
   - **护工自由填写服务时间段**（不与排班自动关联，护工手动输入开始/结束时间）
   - **补卡可不关联排班**（FQ2 已确认：schedule_id 为可空字段）。护工在补卡页面直接填写病人、服务时段和护理内容，即使没有预先生成排班记录也可以发起补卡。
   - **补卡的时间边界判定**（FQ6 已确认）：以**排班所属的日历日期**为准。若排班在周一而护工在周二补提，则判定为跨日，不允许。若补卡无关联排班，则以补卡提交当日的日历日期为边界。
   - 填写护理记录内容后提交
   - 补卡记录标记为 makeup=true，在管理端展示时有特殊标识
   - 跨日补卡一律不允许

4. **缺勤处理**：
   - 排班时间段过后 1 小时仍未提交 → 系统自动标记为旷工
   - 旷工记录在管理端醒目展示
   - 旷工不影响后续排班（Phase 1 不做惩罚机制）

5. **缺勤统计列表（Q25）**：
   - 管理端提供单独的"出勤统计"页面
   - **筛选维度**：按护工（必选）、日期范围（必选）
   - **展示字段**：应出勤次数、实际出勤次数、旷工次数、出勤率
   - **管理员可手动纠正旷工状态**：将某条旷工记录改为"已出勤"，需填写纠正原因，系统保留操作日志
   - **数据模型预留绩效/考核字段**：Phase 1 不展示绩效指标，但在 absenteeism 表中预留 score、performance_level 等字段供后续版本使用

6. **管理端查看**：
   - 管理员可查看所有打卡/护理记录
   - 支持按护工、病人、日期、状态筛选
   - 展示字段：护工姓名、病人姓名、时间、状态（已提交/旷工/进行中）

#### 5.6.3 提醒机制

- 服务时间结束 1 小时后，检查对应排班是否已提交护理记录
- 未提交 → 系统生成一条提醒记录
- 前端通过**轮询**获取提醒列表，**轮询频率为 1 分钟**（Q30，Phase 1 不做实时推送）
- 提醒在护工端以红点/通知栏展示

|------|------|------|
| POST | `/api/checkin` | 开始服务（创建打卡记录） |
| POST | `/api/checkin/:id/submit` | 提交护理记录（结束打卡） |
| POST | `/api/checkin/makeup` | 当日补打卡 |
| GET | `/api/checkin/my` | 护工端：我的打卡记录 |

## 9. 边界情况与错误处理

### 9.1 认证

| 场景 | 处理方式 |
|------|----------|
| 管理员密码忘记 | 通过数据库直连重置（Phase 1 不提供找回密码功能） |
| 护工连续输错密码 | Phase 1 不做锁定机制 |
| Token 过期 | 前端检测到 401 → 清空 token → 跳转登录页 |

### 9.2 护工管理

| 场景 | 处理方式 |
|------|----------|
| 停用护工时有关联排班 | 系统自动取消所有待执行排班（状态变为 cancelled） |
| 停用护工时有关联打卡中记录 | 强制结束当前打卡（标记为 interrupted） |
| 删除护工时存在历史记录 | 逻辑删除，保留历史数据完整性 |
| 身份证号重复 | 新增时校验唯一性，提示"该身份证号已存在" |

### 9.3 病人管理

| 场景 | 处理方式 |
|------|----------|
| 管理员审核自己提交的病人 | 允许，保留操作 audit log（记录操作人、操作时间、操作类型） |
| 护工提交的信息与管理员录入冲突 | AI 检测到冲突时提示护工确认，护工可覆盖或保留双方版本 |
| 病人已分配护工但护工被停用 | 管理员重新分配病人到其他护工 |

### 9.4 排班

| 场景 | 处理方式 |
|------|----------|
| 排班冲突 | 前端+后端双重校验，拒绝提交并展示冲突项 |
| 修改已开始的排班 | 不允许修改已开始服务的排班 |
| 取消进行中的排班 | 不允许取消（需先结束当前服务） |
| 跨天排班 | Phase 1 不支持跨天，所有排班在当天 00:00-23:59 内 |

### 9.5 打卡

| 场景 | 处理方式 |
|------|----------|
| 忘记提交（旷工） | 排班结束 1 小时后自动标记为 ABSENT |
| 补卡（当日） | 允许，记录 makeup=true |
| 补卡（跨日） | 不允许 |
| 同时在多个打卡中 | 不允许，开始新服务前必须结束上一服务 |
| 服务时长不足 1 小时 | 按实际时长记录，不做最短时长限制 |
| 已提交的护理记录需要修改 | Phase 1 不允许修改（只读） |

### 9.6 AI Agent 对话

| 场景 | 处理方式 |
|------|----------|
| AI 提取信息失败 | 返回原始 AI 输出 + 错误提示，护工可手动填写 |
| 网络断连 | 对话内容本地暂存（localStorage），下次进入 session 时恢复 |
| 护工二次确认后反悔 | 提交后不可撤回；如确实需要修改，联系管理员 |
| 病人信息已在之前 session 中完善过 | 进入 session 时提示"已有完整档案，可继续补充新信息" |

### 9.7 缺勤与出勤统计

| 场景 | 处理方式 |
|------|----------|
| 管理员错误纠正旷工 | 需填写纠正原因，系统记录操作人+时间+原状态 |
| 护工对旷工标记有异议 | 线下联系管理员，管理员在系统中纠正 |
| 旷工统计跨月查询 | Phase 1 支持按日期范围筛选（不限当月） |

### 9.8 病人档案版本追踪

| 场景 | 处理方式 |
|------|----------|
| 管理员手动编辑和 AI 补充同时发生 | 以最后提交者为准，系统在版本历史中同时保留两条记录 |
| 护工查看版本历史 | 护工端可见版本历史（只读），便于追踪信息变更 |
| 版本历史无限增长 | 设置合理的数据保留策略（如保留最近 100 条），超过后自动清理旧版本 |

### 9.9 补卡时间与排班一致性（FQ6）

| 场景 | 处理方式 |
|------|----------|
| 护工补卡时填写的时段与排班时段不一致 | 允许，系统分别记录排班时段和实际服务时段，不做强制匹配校验 |
| 补卡的时间边界判定（有排班关联时） | 以**排班所属的日历日期**为准。若排班在周一而护工在周二补提，判定为跨日，不允许 |
| 补卡的时间边界判定（无排班关联时） | 以**补卡提交当日的日历日期**为边界，不允许补录前一天的时段 |
| 补卡时填写的时段跨天 | 不允许，补卡仅限当天 00:00-23:59 内 |

## 10. 依赖与约束

### 10.1 技术依赖

- **AI 服务**：依赖 Anthropic API（Claude），需配置 `ANTHROPIC_API_KEY`

- **离线可用**：Phase 1 不要求离线能力（护工需在联网环境下操作），不提供 PWA（FQ5 已确认）
- **移动端适配**：护工端需适配手机屏幕，Phase 1 为移动 Web（浏览器），**不支持 PWA**（Q28），非原生 App

## 11. Phase 推进逻辑与依赖关系

### 11.1 推荐实施顺序

```
Phase 0: 项目脚手架（基础设施）
  → Phase 1: 认证系统（入口）
    → Phase 2: 病人管理 + 护工管理（基础数据）
```

| 病人管理 | 认证 + 护工管理 | 病人需要关联护工 |
| 排班管理 | 护工管理 + 病人管理 | 排班需要人员和病人数据 |

| 打卡 | 排班管理 | 打卡基于已有排班 |
